# P5：Bundle内資料のAgentジョブと成果物

実装日：2026-09-14。Documents側のソース実装。今回の範囲はBundle内資料の要約・比較で、外部検索、NotebookLM同期、音声は含めない。実API呼出し・実BQ書込・デプロイは行っていない。

## Step 1：依頼をジョブとして保存

Overviewの「この課題の状況」に「資料の処理ジョブ」を追加。資料を取得して本文・手動記録・追加依頼を確認し、ジョブを登録する。登録だけではAIを実行しない。

ジョブはBundleメタデータの独立領域 `thinkAgentJobs` に `schemaVersion: 1` と `jobs` として保存する。ID、処理種類、依頼、登録時Snapshot、状態、各実行の識別子・開始／終了・結果、適用先を記録する。既存の本文・thoughtSupport・P2/P3/P4領域は保全する。

状態は待機中／実行中／成果物候補あり／失敗／中断。ジョブ成功は課題の到達・完了状態へ反映しない。SnapshotはP3と同じBundle内資料形式で、会話履歴・外部資料を自動追加しない。最大300資料・本文120,000文字のP3制限を引き継ぐ。

保存上限は20ジョブ、履歴JSONのUTF-8サイズ2MB。生成結果の保存余地を確保するため、登録時は既存履歴と新Snapshotの合計が1.5MBを超える場合に登録を止める。履歴を自動削除しない。ジョブをJSONで書き出せるが再取込・履歴分割は未実装。

## Step 2：明示実行・中断・再試行

保存済みの送信範囲を確認して実行する。P3のProvider境界と引用検証を再利用し、会話履歴は空で渡す。回答本文をMarkdown成果物候補にし、生成時の引用・ハッシュ・Snapshot ID・Provider・モデル・根拠不足表示を添える。

AI有効化はP3と同じサーバー設定。既定は停止。停止中も登録・履歴閲覧・既に生成済みの候補確認と適用は可能。今回サーバーのキーや有効化設定は変更していない。

処理はHTTP要求中に行い、無人の永続ワーカーは起動しない。1プロセスあたり同時4件まで。AI処理のタイムアウトは120秒、保存された実行期限は180秒。画面切替は元Bundleのジョブへ結果を戻し、別Bundleへ取り違えない。ページ終了等で実行HTTP接続が切れた場合は中断を試みる。

中断はジョブ単位の独立API。会話／音声の停止とは分離している。同一サーバープロセスでは実行中AbortSignalも中断する。別インスタンスに届いた中断は永続状態に反映し、生成結果を採用しないが、外部AI呼出しを即座に停止できる保証はない。

サーバー終了などで実行中のまま残った場合は、期限切れ後に本人が明示的に再実行できる。最大5回。毎回の実行IDで結果を照合し、古い実行結果が新しい試行を上書きしない。再試行は登録時Snapshotを使用し、最新資料へ自動差替えしない。最新資料を使う場合は新しいジョブを登録する。

AIの再実行は再度の利用料金を伴う可能性があるため、ボタンに明示する。失敗・中断履歴を残し、元資料は変更しない。保存先が継続して利用不能になった場合、候補を保存できず実行中状態が残ることがある。その場合は状態再取得・期限切れ後の明示再実行が必要。保存できなかった生成本文をサーバー再起動後に復元する機能はない。

## Step 3：成果物候補と確認後の適用

候補は画面内で全文確認し、Markdownとして書き出せる。本人が追加内容を確認した場合だけ、新しいmemo型Thinkとして追加する。既存Thinkの変更・削除や、Bundleの資料定義への自動追加は行わない。新規ファイルの全文が適用前の追加差分になる。

適用前にクライアントのContextServiceで資料を再取得し、生成時の資料ID／ハッシュと手動記録を比較する。変化がある場合は適用を停止し、書き出しまたは新規ジョブを案内する。この比較はP1の取得可能なクライアント状態を基準とし、実BQ全資料の最新状態や一時点整合性まで保証しない。

サーバーは成果物本文ハッシュと確認時のBundle更新版を検証する。`BigQueryService.applyAgentArtifact`で、Bundleへの適用済み記録と新しいThinkのINSERTを同じトランザクションにする。適用先IDはジョブから決定し、既存IDがあれば上書きしない。適用済みの同一成果物を再試行しても再挿入しない。削除された適用先を自動再作成することもない。

SQL設計の確認資料：[BigQueryの複数ステートメントトランザクション](https://docs.cloud.google.com/bigquery/docs/transactions)。実BQでのSQL実行を検証済みという意味ではない。一般の保存経路による同時書込も含めた環境全体の一意制約を新設したものではない。

適用済みThinkは個別に現在の本文・メタデータを取得してWorkoutで開く。既存の編集中Thinkを置き換えたり、Vault全体の再読込で下書きを消したりしない。

## Step 4：利用手順

BigQueryモードでBundleを開く。

1. 「ジョブと接続状態を取得」で保存状態を確認。
2. 要約／比較と追加依頼を選び、「ジョブの資料を取得」。
3. 資料範囲を確認して登録。
4. 保存済み資料をAIへ送る確認を入れ、ジョブを実行。
5. 候補を確認してMarkdownで保存、または追加内容を確認して新規Thinkへ追加。

実行中の表示は自動ポーリングではなく取得時点の情報。必要に応じて状態取得ボタンで更新する。未保存の依頼はセッション中保持し、ページ終了時に警告する。Electron／Localモードのジョブ保存は未対応。

## Step 5：検証と残作業

テスト対象：登録だけではAIを呼ばない、既定停止、入力・Snapshot・引用検証、試行履歴、中断と完了の競合、旧実行の結果破棄、明示再試行、成果物ハッシュ・保存版、冪等適用、ID衝突、旧データ保全、SQLの更新／挿入境界、送信・適用確認、Bundle切替、資料変更時の適用拒否。

全体回帰は39ファイル・300テスト成功（`npx vitest run --maxWorkers=2 --testTimeout=15000`）。追加したHTTPルートの2テストも成功。フロント・サーバー型検査とサーバービルド成功。新規主要コードのESLintはエラー・警告ともに0件。フロントビルドはサンドボックスの親ディレクトリ読取制限で初回失敗し、通常権限で再実行した。

通常権限でのフロントビルドも成功。既存の大きなJSチャンクに関する警告は継続。
