# P6 続き：連携記録の復元とGemini File Searchの接続確認

実装日：2026-09-14。

自動連携先は、本人の指定により **Gemini File Search** とする。NotebookLMの手動連携は既存の代替経路として維持する。今回は書き出した対応表の再登録と、File Searchの読み取り専用接続確認までを実装した。資料のアップロード・自動同期・検索回答は次段階。

## 連携記録の復元

- 手動連携欄から対応表JSON、または新形式の履歴JSONを選択する。ブラウザ内で形式と対象を検証し、ファイル選択だけでは保存・送信しない。
- 新しい履歴書き出しは`kind: thinktank-external-backup`、schemaVersion 1、Vault ID、Bundle ID、書き出し日時、当該Vaultの履歴を持つ。2MBの保存上限に書き出し時の整形で達しないよう、履歴はコンパクトJSONとする。取込の上限は2,100,000 UTF-8バイト。
- 別Vault／Bundle、履歴内の別Vault、未知バージョン・フィールド、認証情報フィールド、不正URL、不正ハッシュ・重複ID、同期済みを名乗る状態を拒否する。旧形式の対象IDを持たない履歴JSONは帰属を確認できないため取込対象外。対象ID付きの対応表JSONは取込可能。
- 対応表、または履歴中の1件を「復元候補」に選択する。資料のThink IDとハッシュ、旧取得日時、注意事項、Vault一覧に同じIDがあるかを表示する。名称だけで別Thinkへ付け替えない。
- 現在資料を先に取得しておけば、候補選択後にそのSnapshotとの追加・変更・一致・取得できない資料の件数を比較する。取得済みSnapshotとの照合であり、外部サービスや保存先の最新版との一致保証ではない。
- 登録済み記録を取得し、本人確認後に既存の版条件付き保存APIで1件を追記する。旧操作IDを流用せず、保存側の履歴全体を置換しない。復元候補の通信再試行には同じ新操作IDを使う。
- 原本本文・外部Source・外部同期成功の復元は行わない。履歴や対応表は暗号学的に署名されたバックアップではなく、ハッシュもファイル記載値である。現時点の本文が取得できなければ内容の一致は未検証として扱う。

## Gemini File Searchの接続確認

`GeminiFileSearchProvider`を追加し、既存のOpenAI対話Providerとは独立させた。既定は`DisabledFileSearchProvider`。固定のGoogle公式ホストへGETのみを行う。

| 操作 | 実装 |
|---|---|
| サーバー設定を読む | `/api/think-support/file-search/status`。接続ID、有効／停止、読み取り専用モードだけを返す。Googleへ接続しない |
| ストア一覧 | `/api/think-support/file-search/stores`。明示操作でGoogleの`fileSearchStores.list`を1ページずつ呼ぶ。1ページ20件。次ページトークンを保持 |
| 返す情報 | ストアのresource name、表示名、検索可能・処理中・失敗の資料件数、確認日時。件数はint64の精度を失わない文字列、未提供はnull／「不明」 |
| 中断・失敗 | クライアント切断とUI中断を上流へ伝える。15秒で中断。429を区別し、認証・通信・形式エラーの外部本文やキーを返さない |
| 作成・アップロード・検索・削除 | 未実装。ストア一覧取得ではBundle本文を送らず、Bundleとの対応も自動登録しない |

画面は初期表示時にAPIを呼ばない。「File Searchの設定を取得」のあと、「接続先のストア一覧を取得」で初めてGoogleへ接続する。接続に紐づくストアの一覧であり、Bundleに関連付けたストアの一覧ではない。次ページは別の明示操作。表示はその1ページのみで、全件取得済みと扱わない。

設定取得の成功と外部接続の成功は分けて表示する。接続IDが変わった状態で旧ページトークンを送る要求は409で拒否する。ストア名と件数の形式・ページ件数を検証し、ストアの表示名はHTMLとして実行しない。APIキーはヘッダーに載せ、URLやブラウザ応答へ含めない。リダイレクトは追従しない。

## サーバー設定

次の3項目が揃った場合だけ有効になる。今回、実際の環境設定や認証情報は変更していない。

| 環境変数 | 用途 |
|---|---|
| `THINK_SUPPORT_FILE_SEARCH_ENABLED` | 明示的な`true`で有効化 |
| `THINK_SUPPORT_FILE_SEARCH_CONNECTION_ID` | 英数字・ハイフン・下線の安定した接続識別子。認証先のGoogleプロジェクト／アカウントを変える場合は別IDにする |
| `THINK_SUPPORT_FILE_SEARCH_API_KEY` | サーバーで管理するGemini APIキー。ブラウザ・Bundle・会話へ入力しない |

接続IDは管理者が定義する認証参照名であり、Googleから検証済みのアカウントIDを取得する機能ではない。設定はサーバー起動時に読み込む。既存のGoogle／OpenAIキーから暗黙に有効化しない。

## 公式仕様の確認

2026-09-14に[File Search Stores REST仕様](https://ai.google.dev/api/file-search/file-search-stores)を確認した。`fileSearchStores.list`はGET、最大20件のページと`nextPageToken`を持つ。resource name・displayName・int64件数フィールドに合わせて実装した。NotebookLM NotebookのAPIとは統合しない。

[File Searchの公式ガイド](https://ai.google.dev/gemini-api/docs/file-search)も確認したが、利用アカウントでの成功、権限、ストア内資料との対応は実証していない。今回はHTTPレスポンスを模したテストで検証する。
