# P6 続き：BundleとFile Searchストアの対応を保存

実装日：2026-09-14。

## 到達点

前段階の既存ストア一覧に続き、Bundle・Vault・接続IDごとの保存先を登録・変更・解除できるようにした。本人確認後、Googleの既存ストアへのアクセスをIDで再確認し、BigQueryのBundleメタデータへ追記する。今回は資料送信の前提となる対応管理まで。資料のアップロード、検索、外部ストア作成・削除は未実装。

## 操作

1. OverviewのBundle状況で、Gemini File Searchの設定とストア一覧を取得する。
2. 「登録済みのストア対応を取得」で、保存側の版と対応履歴を読む。
3. 接続IDを選び、一覧からストアを選択するか、`fileSearchStores/…`のIDを入力する。
4. 変更前・変更後のIDを確認し、確認チェック後「ストア対応を保存」を押す。
5. 対応を解除する場合は操作を「このBundleとの対応を解除する」にする。Google側のストアと資料は残る。接続停止中・接続ID変更後も、保存済みの接続IDを選んでアプリ内対応を解除できる。

保存先が未取得のときは「未取得」と表示し、「未登録」と混同しない。登録には現在有効な接続IDが必要。解除には登録済みの対応と変更前IDの一致が必要。保存済み履歴はJSONへ書き出せるが、この形式の取込はまだ実装していない。

## 保存・確認の契約

- Bundleの`Metadata.thinkFileSearch`にschemaVersion 1の履歴を追記する。イベントは操作ID、保存日時、Vault ID、接続ID、変更前後のストアID、サーバーが取得したストア確認結果を持つ。
- Vault・Bundle・接続IDごとの最新イベントが現在の対応となる。変更後がnullなら解除済み。表示名では対応を決めず、過去の対応も削除しない。
- `FileSearchProvider.getStore`は固定のGoogle公式ホストへのGETだけを行う。応答のresource nameと要求IDの完全一致を検証する。既定停止、認証のヘッダー限定、15秒の中断、リダイレクト拒否、エラー内容の非公開を維持する。
- 古い一覧結果やブラウザから渡された表示名を確認証拠として保存しない。登録時はサーバーがストアを再取得する。失敗、不正応答、ID不一致、中断時には新しい対応を保存しない。
- ストア確認日時はアクセス確認であり、資料同期成功日時ではない。元資料ハッシュ、外部Document ID、同期Operation IDの保存は次段階。
- Bundleの版と変更前ストアIDを確認してから外部照会し、照会後のBQ更新にも版条件を付ける。間に別の保存があれば409。旧本文、手動記録、対話、Agent、NotebookLMの手動連携メタデータを維持する。
- 同一操作IDの同じ入力は履歴追加や外部照会を繰り返さず保存結果を返す。異なる入力なら409。保存結果が不明な場合は入力を変えず再試行できる。履歴は100件／2MBで停止し、自動削除しない。
- UI下書き・処理中状態はVaultオブジェクトとBundle単位に保持する。切替後の遅延応答は元の対象へ返す。入力変更・再取得で本人確認を解除する。保存方式は既存同様BigQueryモードに限定する。

この段階は「各Bundleに接続ごとに1ストア」の管理であり、別Bundleによる同一ストアの使用を全体で排他制御する機能ではない。ストア内に他用途の資料が存在し得るため、検索回答を接続する際にはDocumentとThinkの対応・範囲制約が別途必要。
