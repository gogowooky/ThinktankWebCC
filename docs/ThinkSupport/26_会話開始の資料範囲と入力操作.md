# 会話開始の資料範囲と入力操作

更新日：2026-09-19。

## 準備が終わらない問題

実画面ではOverviewが「全Thinkファイル（5,481件）」を選択していた。AI設定と選択Chatの履歴取得は正常だったが、ThinktankもOverviewの資料を無条件に参照しており、大量の本文取得を会話開始前に待つ構成になっていた。

Thinktankの会話は資料なしを既定とし、「Overviewの資料を使う」を明示的に選択した場合だけBundleを参照するように変更した。資料の使用を切り替えても下書きを維持する。未保存回答がある間は切替を禁止し、復帰時もその回答の資料範囲を維持する。

会話用ContextServiceには300件の上限を渡す。上限を超えた場合は各資料の本文取得前に絞り込みを案内し、取得できた一部だけを黙って送信しない。一般のContextService利用者にはこの上限を強制しない。

実ブラウザで資料なしの準備完了と、「こんにちわ」入力後の送信ボタン有効化を確認した。9月19日に同じChatの履歴APIを照会し、保存済み3往復を確認した（会話本文は診断出力に含めていない）。

## 待機表示とキーボード送信

準備・回答生成・保存中の表示の先頭に回転するインジケーターを追加。OSの動きを減らす設定では静止する。回答生成表示は主にAI応答の待機を表すが、サーバーの履歴確認や応答検証も含み、AIの内部処理の進捗率は示さない。

Enterで送信、Shift+Enterで改行に対応。日本語変換中・変換確定のEnter（composition状態、isComposing、keyCode 229）は送信に使わない。準備中・回答生成中・未保存回答がある間の送信と二重送信を防止する。入力欄に操作案内を表示する。

## 保存方式の説明

Chatを選択したAIChatでは回答後に質問・回答をChat本文へ同期し、引用・提案等を同じChatのthinkConversationsメタデータに保存する。保存先はBigQueryで、JSON書き出しは任意の控えである。これを「参照情報・その他」に明記した。Chat未選択のBundle会話ではBundleの履歴へ保存する旨を表示する。

入力中・回答待ちの質問はまだ永続保存しない。保存失敗時の回答は画面内に保持して再試行・書き出しできる。保存処理中に「回答を保存できませんでした」と誤表示しないよう修正した。

「この相談を課題として始める」は、課題名・会話からの目的と完了条件の候補を確認後にBundleを作成し、元Chatを関連付け、Overviewで開く既存機能。完了や実行を自動確定する操作ではない。

## 検証

### 追加：操作リンクと案内の整理

会話本文に毎回付けていた「根拠不足・未確認事項を含みます。」の定型表示を廃止し、「参照情報・その他 → 会話記録の確認・書き出し → 各会話」の詳細内へ移動した。回答本文の不確実性に関する説明と、保存済みのinsufficientEvidence情報は保持する。

再試行・書き出し・出典・課題化などの補助操作は、読みやすさを保った淡い文字色と下線で表示する。エラー文と対応操作は一つの通知枠にまとめ、入力欄下では左にEnter／Shift+Enterの案内、右に枠付きの送信ボタンを置く。狭い幅では折り返し、詳細な参照情報は区切り線の下へまとめる。実ブラウザでリンク表現・入力欄下の配置を目視確認した。既存の下書きは保持し、検証のための送信は行っていない。

関連3ファイル・48テスト、フロント・サーバーの型検査、変更TSXのLint、差分の空白検査、本番ビルドに成功。ビルドにはimport混在・チャンクサイズ警告が残る。アニメーションの実画面での見え方とキーボードによる実API送信は今回未確認。

## 追加：入力操作を履歴のスクロールから分離（2026-09-19）

会話欄は面全体が一つのスクロール枠で、入力欄・送信・課題化まで履歴と一緒に流れていた。履歴を遡ると入力欄が画面外に出て、前の発言を見ながら書けない。スクロールを会話ログだけに持たせ、Chat名は上端、入力帯は下端に固定した。入力帯には「この相談を課題として始める」「Overviewの資料を使う」「待機表示」「保存失敗の通知」「入力欄」「Enter案内と送信」「参照情報・その他」を置く。参照資料の展開などで入力帯が伸びても会話ログを潰さないよう、入力帯は領域の55%で頭打ちにして内側でスクロールさせる。新しい回答はログを末尾へ自動で寄せて表示する。

表示は次のとおり簡素化した。一問一答の枠を廃止し、往復の区切りは余白だけにする（狭いパネルでは枠のぶん本文が細り行数が増える）。入力欄の上と送信行の下の区切り線を廃止する。送信は他の操作と同じリンク表現（下線）にし、色だけ本文と同じにして補助操作より前に出す。スクロールバーの溝は色を置かずチャットエリアの地色を透かし、バーは右余白へ食い込ませる。`scrollbar-gutter: stable` で居場所を常に確保するので、バーの出入りで本文の右端は動かない。

保存済み会話のJSON書き出しは、保存が成功した記録の控えでしかなく利用目的が無いため廃止した。保存に失敗した回答の「回答を書き出す」は、画面を閉じると失われる唯一の復旧手段なので残す。「質問と回答は回答後に自動保存します」の案内は仕様として確定したため表示しない。「参照情報・その他」には、AIの接続状態、今回の参照資料（`chat-only` なら「参照資料なし」、Bundleを使う場合は件数と各資料の本文）、会話記録の確認を残す。書き出しが無くなったので、この項目名は「会話記録の確認・書き出し」から「会話記録の確認」に変えた。

「会話記録の確認」の中身も、turnの生JSONを出すのをやめ、1往復を1行にまとめた（`日時 ／ provider / model ／ 参照資料あり・なし ／ 根拠不足あり・なし`）。本アプリの利用者は記憶や時間の余裕を補いたい人で、構造化記録をそのまま読む前提が置けない。1行に残した4項目は、会話欄からは読み取れずここにしか無い情報である。特にモデルを切り替えながら相談したとき、どの回答をどのAIが答えたかは上部の「AI：」表示（＝今の設定）では分からない。旧テキスト形式から復元した会話は `legacy-text / stored-chat-text` と表示される。insufficientEvidence の説明文は「根拠不足あり」の1語に置き換えた。

実ブラウザ（Thinktank＞会話履歴、保存済みChat選択）で確認した。`.support-conversation` は自身ではスクロールせず、会話ログだけが独立してスクロールし、先頭までスクロールしても入力欄は動かない。「参照情報・その他」を開くと入力帯は55%で止まり会話ログは残る。Chat名・会話ログ・入力欄の右端はすべて同じ位置に揃い、スクロールバーは右余白に収まる。ThoughtSupport 12ファイル・68テスト、フロントの型検査、変更ファイルのLintに成功。実APIへの送信は行っていない。

## 追加：会話面の整理（2026-09-19）

会話欄に常時出ていたものを、使う頻度で置き直した。

会話記録は「参照情報・その他」の一覧をやめ、各一問一答の直下に記録アイコン（lucide `file-json`。`file-braces` はlucideに無く、ファイルに波括弧を描く同義のアイコンを使う）を置いた。押すとダイアログで当該turnのJSONを表示し、「保存する」で書き出せる。枠は「フィルター選択」（`ColumnSortDialog.css`）を流用し、位置だけ会話面に合わせる（`.bundle-conversation` を `position: relative` にして `inset:0` の背景が会話面に収まるようにした）。「×」または背景クリックで閉じる。前節で1行要約に変えた一覧は、これに置き換わって廃止した。

「参照情報・その他」を「条件・機能・参照情報・その他」に改称し、「この相談を課題として始める」と「Overviewの資料『…』を使う」をこの中へ移した。どちらも会話のたびに触るものではない。入力帯に常時出ているのは、待機表示・保存失敗の通知・入力欄・送信だけになった。

Chat名の見出しは廃止した。上のChat一覧の選択行に同じ名前が出ており、狭いパネルで2行を同じ情報に使う理由がない。入力欄の外に出していた「Enterで送信 · Shift+Enterで改行」も廃止し、空欄時のプレースホルダ「メッセージを入力、Enterで送信 · Shift+Enterで改行」に統合した。入力済みのときは案内が消えるが、その時点では操作を覚えている前提で足りる。会話の話者表示は「本人：」から「You：」に変えた。

実ブラウザで確認：Chat名の見出しが無いこと、話者が「You：」であること、プレースホルダの文言、欄外の案内が無いこと、折りたたみの見出しが「条件・機能・参照情報・その他」で中に課題化リンクが入ること、記録アイコンが各一問一答の直下（会話ログ内）に出ること、ダイアログが会話面の内側に開き見出し・×・保存する・JSON本文のスクロールを備え、×と背景クリックの両方で閉じることを確認した。全61ファイル・441テスト、フロントの型検査、変更ファイルのLintに成功。実APIへの送信と書き出しの実行は行っていない。

## 追加：余白の排除と送信操作の一本化（2026-09-19）

Chat一覧の下は「余白・会話ログ・余白・入力帯・余白」の5段になっていた。会話ログも入力帯もそれぞれスクロール枠を持つので、外側に帯を挟むぶんだけ読める行と押せる場所が減る。上下の余白を全廃し（`.support-conversation` の `padding` を `12px` から `0 12px` へ、入力帯の `margin-top` を削除）、左右だけ本文が枠に貼り付かないよう残した。

待機表示・失敗の文言を送信行へ移した。入力欄の上に通知の帯が積み上がるほど、送信までの距離が伸びて画面も細切れになる。送信行は左に文言、右に操作（中断／準備を中断／送信）を置き、狭い幅では文言側が折り返す。文言が無いときは `:empty` で行ごと消える。

「再試行」を廃止し、送信に一本化した。従来は準備に失敗すると「再試行」で取り直してから「送信」を押す二段構えだったが、押し分けても結果は同じで、失敗のたびに別のボタンを探させていた。送信は、準備が済んでいなければ先に取り直し、成功したらそのまま送る。`prepare()` が準備結果（資料と履歴）を返すようにして、stateの反映を待たずに送信へ渡す。**これによりv1.5.13の「再試行はAIを呼ばない」性質は失われる**が、押すボタンの名前が「送信」である以上、送信されることは利用者の意図と一致する。AI停止中（`status.enabled === false`）は取り直しても送れないので、送信は無効のままにする。「保存を再試行」は保存のみの再試行で別物なので残す。

折りたたみは「条件・機能・参照情報・その他」から「条件・機能・参照情報」に改め、中を3つの小見出しに分けた。条件＝「Overviewの資料『…』を使う」、機能＝「この相談を課題として始める」「進行を見直す質問を入力」、参照情報＝AIの接続状態と「参照資料：なし／N件」（資料がある場合は内訳）。該当するものが無い区分は見出しごと出さない。

実ブラウザで確認：Chat一覧の下から入力帯の下端まで、3か所の縦の余白がいずれも0px。長いエラー文言を送信行に入れても送信は同じ行の右端に残る（文言側が折り返す）。折りたたみの見出しと3区分の中身、単独の「再試行」ボタンが無いことを確認した。全61ファイル・441テスト、フロントの型検査、変更ファイルのLintに成功。実APIへの送信は行っていない。

### 追加：折りたたみ内の字下げと入力欄の高さ

「条件・機能・参照情報」の最下に12pxの余白を置いた。入力帯はスクロール枠なので、最後の項目が枠の下端に貼り付くと、まだ続きがあるのか終わりなのかが読めない。入力帯がスクロールする状態でも末尾まで送ったときに余白が残ることを確認した。

各小見出しの下の項目は全角1文字ぶん（`margin-left: 1em`）字下げした。区分の見出しと項目が同じ行頭に並ぶと、どの区分に属する項目かを毎回読み直すことになる。チェックボックスと文言の間には半角スペースを入れた。

メッセージ入力欄の高さ（`min-height`）を90pxから60pxへ下げた。入力欄が空でも3行ぶんの高さを取っていて、そのぶん会話ログが短くなっていた。縦方向のドラッグでの拡大は従来どおり残す。

### 追加：折りたたみを開いたら中身まで送る

「条件・機能・参照情報」を開いても、増えた中身が入力帯の下にはみ出したままだと、何が出たのか分からない。開いたときに入力帯をスクロールし、中身の下端が見える位置まで送る。中身が入力帯より背が高くて収まらないときは、代わりに先頭を上端へ寄せて、そこから読み下せるようにする。

`requestAnimationFrame` は使わない。描画されていないウィンドウでは呼ばれず、送りそこねる（実機で確認：`document.visibilityState === 'visible'` でも600ms以内に発火しない状態が起きる）。`getBoundingClientRect` が同期でレイアウトを確定させるので、`toggle` ハンドラ内でそのまま測って `scrollTop` を代入する。

実ブラウザで2通りを確認した。中身が収まる場合（入力帯191px／中身171px）はscrollTop 94で上端・下端とも見える。収まらない場合（入力帯119px／中身171px）は中身の先頭が入力帯の上端に揃う。

### 追加：区分そのものを折りたたむ

「条件」「機能」「参照情報」の3区分を見出し（`h4`）から `details` に変えた。普段は畳んでおき、必要な区分だけ開ける。外側の「条件・機能・参照情報」を開いたときは、3区分もまとめて開く。区分をひとつずつ開かせると、何がどこにあるかを覚える負担が増えるため。外側を閉じて開き直したときも、中で閉じたものを含めて全部開き直す。

React の `onToggle` は入れ子の `details` からも親のハンドラへ届くので、`event.target !== event.currentTarget` のときは何もしない。この番人が無いと、中の区分を閉じただけで3区分が開き直され、スクロールもやり直される（実機で確認済み）。

実ブラウザで確認：外側を開くと3区分が同時に開き、中身全体が入力帯に収まる位置までスクロールする。区分を1つ閉じても外側は開いたまま、他の区分もそのまま、スクロール位置も動かない。外側を閉じて開き直すと、閉じていた区分も開く。項目の字下げ（区分の見出し52.0px→項目63.7px）は維持。全61ファイル・441テスト、型検査、Lintに成功。
