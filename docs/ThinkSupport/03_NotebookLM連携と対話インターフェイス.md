# NotebookLM連携・対話インターフェイス設計

作成日：2026-09-13。区分：合意方針と設計案。

本書は連携の要求と構成案を定める。NotebookLM、Gemini File Search、音声APIの現行機能・契約・制限を確認した接続仕様ではない。外部サービスの能力は実装前に公式仕様と利用アカウントで検証する。現行アプリにこれらの同期・対話機能は未実装である。

## 1. 名前と正本

Bundleの名称と内部IDは当面維持する。Notebookへの全面改名は将来検討とする。先の議論で提案された「内部NotebookをBundleの上に設ける」構成も採用確定ではなく、初期連携には要求しない。

ThinktankのBundleを、資料範囲と関連記録の正本とする。外部Notebookや検索Storeは、その資料を利用する接続先として扱う。外部サービス側の変更を自動的にThinktankの確定情報にしない。

## 2. 三つの対象を区別する

| 対象 | 役割 | 実装上の関係 |
|---|---|---|
| Thinktank内の新Overview | 資料、質問、引用、思考状態、成果物を扱うUI | 外部同期がなくても利用可能にする |
| Google NotebookLM | 外部のNotebook単位の作業空間 | NotebookLMConnectionを介した同期先の候補 |
| Gemini File Search | 資料検索・回答の根拠取得に利用する候補 | Store／Document対応を持つ別アダプター |

NotebookLMの画面を埋め込む構成を優先しない。Gemini File Searchを採用しても、それだけでNotebookLMのNotebookや会話と同期できるとは扱わない。両者の実装可否・認証・ID体系は別々に確認する。

## 3. 同期モデル

初期の目標は「1 Bundle = 1 Notebook」。厳密には、同じVault・Bundle・接続アカウント内で1つの対応を持つ設計とする。アカウント切替や複数接続先の扱いは、重複作成を防ぐため接続情報に含める。

| Thinktank側 | NotebookLM連携案 | File Search連携案 |
|---|---|---|
| Bundle | 外部Notebook | 外部Store |
| Think | 外部Source | 外部Document |
| Thinkの版・ハッシュ | 同期済みSourceの版との対応 | 登録済みDocumentの内容との対応 |
| 回答の引用 | 取得できる引用情報からThinkへ対応付ける | 取得できる引用情報からThinkへ対応付ける |

1 Thinkを複数の外部資料に分割する場合、対応表は1対多を表現できるようにする。初期は対応可能なテキスト資料から始め、添付ファイルや複雑な形式の抽出は対象範囲を別途決める。

## 4. 同期記録の案

保存場所は未確定。既存Bundleメタデータへ直接混在させる案と、専用接続レコードを置く案を比較し、まずは非破壊で追加できる形を選ぶ。

| 単位 | 項目案 | 用途 |
|---|---|---|
| 接続 | connectionId、vaultId、bundleId、接続先種別、アカウント識別子 | 正本と外部接続を識別する |
| 外部コンテナ | notebookLmNotebookIdまたはfileSearchStoreId | 名前変更に影響されない対応 |
| 起源 | createdByThinktank、対応表の版 | 再関連付けと外部取込を区別する |
| 資料対応 | thinkId、externalSourceIdまたはexternalDocumentId、必要なら分割番号 | 外部引用からThinkへ戻る |
| 内容 | sourceRevision、contentHash、hashAlgorithm、normalizationVersion | 更新・再送の要否を判定する |
| 同期 | lastSyncedAt、lastAttemptAt、status、lastError、operationId | 成功と試行を区別し、再試行を管理する |

秘密鍵やアクセストークンの値はBundle本文やブラウザ保存設定に入れない。接続情報には安全な資格情報管理への参照を持たせる。

ハッシュは実際に外部へ送った内容から計算する。本文の正規化やファイル抽出方法が変わった場合を区別できるよう版を記録する。最終同期日時は成功後に更新し、失敗した試行時刻で上書きしない。

## 5. 同期と再関連付けの手順案

1. ContextServiceでBundleの資料範囲と版を解決する。動的検索条件はその時点の結果を固定する。
2. 保存済み対応表と外部の取得可能な状態を読み、新規・更新・欠落・競合を分類する。
3. 送信する資料と差分を提示し、合意した送信範囲で同期する。
4. 成功したSource単位でID・ハッシュ・日時を保存する。部分失敗は成功済みと分けて残す。
5. 再試行では操作IDと対応表を使い、外部NotebookやSourceの重複作成を避ける。

Thinktankが作ったNotebookは、保存済み外部IDとBundle IDの対応を優先して再関連付けする。タイトルや内容の類似度だけで確定しない。対応表を失った場合、外部APIが起源情報を保持・取得できるか検証し、できなければ本人による候補確認を必要とする。「高精度で再関連付け」は対応情報を保全する設計によって実現する。

初期同期では外部Sourceの削除やローカル資料の削除を自動伝播させない。参照解除・外部削除・完全削除を区別し、欠落は同期状態として示す。再接続時の上書きも差分確認を経由する。

## 6. 外部で作成されたNotebookの取り込み

外部Notebookは、利用可能なAPIやエクスポートで取得できるSource情報を中心に扱う。元URL、タイトル、取得できた本文・ファイル、外部ID、取得日時、取得方法を来歴として残す。

会話履歴、内部メモ、生成物、資料構造を完全に復元できるとは約束しない。取り込み前に取得可能項目と欠落項目を表示する。既存Thinkとの一致候補は提示できるが、名前だけで統合しない。

利用アカウントで同期APIが使えない場合の代替は、Bundle資料の手動エクスポートと外部Notebookへのリンク登録である。自動同期と同じ状態表示にしない。外部画面の自動操作を暗黙の代替実装としない。

## 7. Bundle内回答と外部検索

| モード | 根拠の範囲 | 回答の条件 |
|---|---|---|
| Bundle内資料のみ | 選択したSnapshotの資料 | 根拠不足は「資料からは分からない」と示す |
| 外部検索を含む | Snapshotに加え、明示した外部検索結果 | 外部出典・取得時点・推論を区別する |

モードは送信前と回答の両方に表示する。Bundle内モードで検索結果が足りない場合、外部検索へ自動で切り替えない。外部検索で見つかった資料は候補として提示し、Bundleへ追加する操作を分ける。

引用は単なる出典名ではなく、Think IDと参照版、可能なら本文範囲・ページ位置まで対応付ける。出典を解決できない引用は未解決として示す。回答後に資料が変わった場合は、現在版と回答時点の版の差を示す。

## 8. テキスト対話

送信時に、対象Bundle、資料範囲、回答モードを固定してConversationServiceへ渡す。応答には本文、引用、未確定事項、変更提案を分けて持たせる。

対話中に本人が別Bundleを開いても、進行中応答の保存先は変えない。対象の変更は次の発言または明示的な切替として扱い、履歴から参照対象を追跡できるようにする。

「目的を整理する」「候補を比較する」「不足を調べる」「次の行動を決める」など、意図に基づく入口を設ける案とする。AI会社名やモデルは設定・詳細情報で確認できるようにする。新規UIの最初の段階はテキスト対話に限定する。

## 9. 音声対話

将来のConversation AIとしてOpenAIの音声を候補とする。採用前に公式仕様、認証方式、ブラウザ・Electronの対応を検証する。

UIには録音中・送信中・応答中・停止状態を明示する。発話途中の文字起こしと確定した発言を分け、本人が修正できるようにする。「はい」のような短い発言だけで重要な決定を確定せず、確認対象と結び付けて扱う。

割り込み時は音声再生と応答生成を中断する。Agentが開始済みの場合、その処理の中断は別に管理する。音声が使えない場合はテキストへ戻れる。録音音声を保持するか、確定テキストのみ保持するか、保存期間をどうするかは実装前の確認事項とする。

## 10. Agentへの処理依頼

対話から「この資料を比較表にする」などの依頼をAgentServiceへ渡す。UI上で依頼内容、入力資料、進捗、中断、再試行、成果物を追跡できるようにする。

処理状態の案はqueued／running／awaiting_confirmation／succeeded／failed／cancelled。これは思考の検討完了・意思決定完了などとは別の状態である。ファイル生成が成功しても本人の課題全体を自動で完了にしない。

成果物は新しいThink候補、または既存Thinkへの差分として提示する。適用時に基準版を照合し、別操作で変更されていれば再確認する。再試行による二重生成・二重適用を防ぐ。

## 11. 接続前の検証項目

- 対象サービス・契約・アカウントでNotebook、Source、引用の作成・取得・更新が可能か。
- IDの安定性、権限、レート制限、ファイル形式、容量、データ保持・削除条件。
- 外部NotebookのSource取得範囲と、取得できない情報の説明方法。
- LAN Local AIの接続・認証・能力と、接続失敗時の挙動。
- 実資料を送らない検証データによる同期・再試行・切断復帰の実証。

確認結果には公式資料のURL、確認日、対象アカウント種別、実証結果を残す。未検証の項目を製品機能として案内しない。
