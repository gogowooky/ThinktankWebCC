# P4：進行・到達状態と再開支援

実装日：2026-09-14。Documents側のソース実装。実データ移行・外部AI送信・デプロイは行っていない。

## Step 1：到達状態を独立した記録にする

検討・意思決定・実行・検証を独立した4項目とし、それぞれ「未記録」「到達」「再検討」「対象外」を選ぶ。実行だけの到達も記録でき、すべての段階を強制しない。保留は別項目として扱い、再開時は保留を外して理由を記録する。

これは今回採用した実装上の出発点。旧Chatタイトルの「完了」、P2の段階、AI提案から自動変換しない。課題全体を自動的に「終了」と判定する仕組みではない。

## Step 2：本人確認・根拠・再開情報

Overviewの「この課題の状況」に「進行と到達状態」を追加。明示的な取得ボタンから保存済みの状態、目的・次の行動・完了条件、再開メモを確認する。入力は保存済みの表示と分離する。

保存時は根拠・変更理由と残課題の扱いを必須にする。残課題がない場合も本人が「なし」と記録する。保留時は再開条件を必須にし、再開要約・再確認日を任意で残せる。根拠資料はContextServiceから選び、Think IDとSHA-256を記録する。本文が変わった場合や未取得の場合は確認を促す。引用元の現在のThinkをWorkoutで開ける。

再確認日はアプリ内の表示だけで、自動通知やバックグラウンド監視は行わない。本人確認はチェックボックスとサーバー記録時刻であり、本人の認証IDや根拠の真実性を証明するものではない。

## Step 3：履歴と競合

Bundleメタデータの独立領域 `thinkProgress` に `schemaVersion: 1` と `events` を保存。イベントには操作ID、連番revision、本人確認時刻、author=human、入力全体を記録する。保留・再開・到達の見直しも追記し、前の記録は消さない。

P2のBQトランザクションによる版照合を使用し、本文、旧thoughtSupport、P2のthinkSupport、P3のthinkConversationsを保全。競合時は入力を保持し、最新記録と比較して本人が再確認する。入力不変の保存再試行では同じ操作IDを使用し、保存成功後に応答だけ失われたケースでも重複追加しない。

履歴の上限は100件またはUTF-8 JSONで2MB。上限到達時に自動削除せず書き出しを案内する。保存済み履歴と未保存入力をJSONで書き出せる。再取込は未実装。

下書きはVaultオブジェクト・Bundle単位でセッション中保持。遅延した取得・保存は元のBundleへ反映する。ページ終了時に警告するが、強制終了後の復元は保証しない。Electron／Localでは既存記録の閲覧のみで、保存はBigQueryモードを対象とする。

## Step 4：進行を見直す候補

AIなしの候補表示は、P2の目的・次の行動・完了条件の未記録、直近3回の同一質問、直近3回の根拠不足を確認する。採用・完了は自動確定しない。質問の一致は前後空白を除いた文字列一致であり、意味的な繰り返しや本人の停滞を断定するものではない。

P3の対話欄に「進行を見直す質問を入力」を追加。目的からの逸脱の可能性・繰り返し・根拠不足と、次の一手・保留・終結候補を確認する質問を用意する。既存の質問を上書きせず、質問準備だけでは送信しない。P3の資料確認・送信確認・既定停止を維持する。応答は既存の引用検証と未採用提案の経路で扱う。

P3へ送る資料範囲は従来どおり。P4の到達状態全履歴をAIへ自動送信する変更は含めない。意味的な逸脱検出の精度や終結提案の妥当性は実モデルで未検証。今回の到達点は、本人の状態記録と見直しの入口であり、無人の統括AIではない。

## Step 5：検証と残作業

新規テストは、独立到達状態、保留条件、日付・出典検証、旧完了の非変換、保留と再開の履歴、本人確認必須、メタデータ保全、競合、冪等保存、Bundle切替、遅延読込を対象とする。

最終確認は全36ファイル・285テスト成功（`npx vitest run --maxWorkers=2 --testTimeout=15000`）。最初の全体実行では既存Overviewテスト1件が5秒制限でタイムアウトしたが、並列数を抑えた再実行で成功した。タイムアウトのために製品コードや既存テストは変更していない。P4画面の4テストも個別成功。型検査と両ビルド、新規主要コードのESLintに成功。フロントビルドは初回のサンドボックス読取制限後、許可された通常権限で再実行した。既存の大きなJSチャンク警告は継続。

実BQの保存・再読込、実画面の操作、P3の実OpenAI接続、P0の復元確認は未実施。実サービスを使う次の検証では、検証用Bundle／保存先と利用モデルを確定し、P2→P3→P4の保存・再取得・競合を順に確認する。既存のキーや有効化設定は変更していない。
