# AIによる思考支援の枠組み

作成日：2026-09-13。区分：合意方針と設計案。現状の実装範囲は末尾に記す。

## 1. 本アプリが支援すること

Thinktankは、本人が考えていること、集めた資料、過去の判断を継続して扱い、「今、何を考えるべきか」「何が決まったか」「何をすれば終えられるか」を明確にするアプリである。

AIの回答そのものを最終成果とはしない。根拠のある判断、実行可能な次の行動、後から検証できる記録を成果とする。途中で中断しても目的・経緯・残る論点を取り戻せることも重要な機能である。

## 2. 思考支援の循環

| 段階 | 本人が行うこと | AIが支援すること | 残す記録 |
|---|---|---|---|
| 問いを定める | 気になること、目的、制約を示す | 曖昧な問いを整理し、必要な確認を絞る | 目的、対象範囲、完了条件 |
| 資料を集める | 対象のThinkとBundleを選ぶ | 不足資料や比較軸を提案する | 資料ID、出典、取得・参照時点 |
| 検討する | 仮説や選択肢を比較する | 要約、比較、反証、矛盾・不足の提示 | 暫定結論、根拠、残る論点 |
| 決める | 採用案と見送る案を判断する | 判断理由と不確実性の整理 | 本人の決定、その根拠、確認日時 |
| 実行する | 行動し、必要な処理を依頼する | 手順化、資料作成、Agentへの処理依頼 | 次の行動、成果物、実行結果 |
| 検証する | 目的・完了条件を満たしたか確かめる | 結果と期待の比較、残課題の抽出 | 検証根拠、到達状態、残課題 |
| 再開・終結する | 続行、保留、終了を選ぶ | 再開要約と終了可能性の提示 | 再開条件、保留理由、終結理由 |

これは固定した一方向の手順ではない。不足資料が見つかれば収集へ戻り、実行結果が想定と異なれば判断を見直す。

例：イベント準備のBundleで、会場候補と条件を比較し、本人が会場を決める。この時点は意思決定完了であり、予約や開催、結果確認まで完了したとは扱わない。

## 3. 常に確認できる思考状態

| 項目 | 意味 | 記録上の扱い |
|---|---|---|
| 目的 | 何のために考えるか | 本人の意図を基準にする |
| 段階 | 現在どの作業をしているか | 完了状態とは分ける |
| 暫定結論 | 現時点で支持される見立て | 仮説であることと根拠を明示する |
| 決定事項 | 本人が採用した判断 | AI提案とは別に保存する |
| 残る論点 | 未解決・矛盾・不足情報 | 不明を空欄や解決済みに変換しない |
| 次の行動 | 次に行う具体的な一手 | 担当・条件・期限は必要な場合に記録する |
| 完了条件 | 何を満たせば終えられるか | 検証可能な形で定める |

各項目には出典Think、更新日時、提案か本人確認済みかを付ける設計とする。資料の事実、AIの推論、本人の決定を混ぜない。既存の`proposals`を自動的に暫定結論へ、`current`を段階へ読み替えない。

## 4. サービスの責務

| 構成要素 | 責務 | 主な入出力 |
|---|---|---|
| ContextService | 対象Bundleの資料と思考状態を読み取り、共通の参照状態を作る | Bundle ID → ContextSnapshot |
| ConversationService | 本人との対話、問い直し、理解の確認を扱う | 発言＋Snapshot → 応答と変更提案 |
| AgentService | 調査、分析、ファイル処理を実行単位で管理する | 依頼＋Snapshot → 進捗・成果物・適用差分 |
| AIProvider | 各社・Local AIの能力と呼び出しを抽象化する | 能力指定＋入力 → 応答・中断・エラー |
| 変更適用の境界 | 提案を正本に反映し、履歴と競合を管理する | 承認済み変更＋基準版 → 保存結果 |

Conversation AIとAgentは同一の会話履歴やモデルに密結合させない。どちらもContextServiceの同じSnapshotを参照し、資料範囲や判断の根拠を共有する。変更適用の境界は設計上の責務であり、クラス名や保存先は未確定である。

OpenAIのテキスト・音声を将来の候補とする。Claude、Gemini、LAN内Local AIにも置き換え可能な境界を設ける。各モデルが音声・ツール・ファイル処理を同程度に提供するとは仮定せず、能力に応じて選択する。

## 5. ContextSnapshotの設計案

Snapshotは「その応答・処理が何を根拠にしたか」を後から説明するための参照記録である。

- 識別：snapshotId、vaultId、bundleId、作成日時、スキーマ版。
- 資料範囲：Bundle定義の版、解決済みThink ID、各Thinkの版またはハッシュ、引用に必要な位置。
- 思考状態：前節の項目、その出典、本人確認の状態。
- 品質情報：未読・欠落資料、抽出失敗、内容の矛盾、古い資料の警告。
- 利用範囲：Bundle内のみか、外部検索を許可した処理か。

Bundleは直接参照だけでなく検索条件や他Bundleの参照を持てるため、同じBundle IDでも資料範囲が変わり得る。IDだけを会話に付ける方法では参照時点を再現できない。Snapshotの本文をどこまで保存するかは、容量・保存期間と併せて決定する。

欠落資料があるときは、不完全な範囲を表示する。別Bundleや全Vaultへ無断で検索を広げない。複数会話で異なる決定が記録されている場合、最新の一つを無条件で正解とせず、競合として本人に示す。

## 6. 統括AIの役割

統括AIは、独立した人格や別モデルを必須とせず、対話・処理を目的へ向ける制御上の役割として設計する。

目的からの逸脱、同じ議論の繰り返し、次の行動が決まらない状態を見つけ、要約や問い直しを行う。十分に検討できた場合は「何が満たされたので次へ進めるか」を示す。残課題があれば、解決・別課題化・保留のどれとして扱うか提案する。

本人の判断、外部への影響を伴う処理、終了の確定をAIの応答だけで済ませない。応答生成と記録変更を分離し、確認する内容が具体的な差分として見えるようにする。

## 7. 進行と終結の区別

| 到達状態 | 意味 | 必要な根拠の例 |
|---|---|---|
| 検討完了 | 必要な比較や論点整理が終わった | 比較結果、未解決事項の扱い |
| 意思決定完了 | 本人が方針を選んだ | 本人の発言、採用理由 |
| 実行完了 | 決めた行動を実施した | 作業記録、成果物 |
| 検証完了 | 実施結果を条件に照らして確認した | 検証結果、確認者・日時 |
| 保留 | 現在進めず、再開条件を残した | 理由、待つ情報、見直し時期 |

保存形式は未決定。単一の状態選択にするか、各到達状態を独立して保持するかは、実例で確認する。すべての課題に全段階を強制しない。従来の「完了」を一律に検証完了へ移行しない。

## 8. 成功を測る観点

評価は回答の自然さだけでなく、次の観点で行う。数値目標は利用例を収集してから設定する。

- 再開時に目的と次の行動へたどり着けるか。
- 判断・結論から出典へ戻れるか。
- AI提案を本人の決定と誤認するケースを防げるか。
- 根拠不足で回答できないときに不足を説明できるか。
- 行動・検証まで進んだか、終結理由と残課題が残るか。
- AIが停止していても資料整理・編集・保存が続けられるか。

## 9. 現状との境界
