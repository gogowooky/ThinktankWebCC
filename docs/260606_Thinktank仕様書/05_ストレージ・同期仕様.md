# Thinktank アプリケーション仕様書：05. ストレージ・同期仕様

本ドキュメントは、アプリケーションで扱うデータの永続化を担うストレージバックエンドの切り替え仕組み、各ストレージ（Local / BigQuery）におけるCRUDおよび検索の内部ロジック、およびデスクトップクライアントとクラウドサーバー間の差分同期仕様について定義します。

---

## 1. バックエンド切り替えと共通インターフェース

アプリケーションは、実行環境を自動チェックして適切な永続化バックエンドを切り替えるシングルトンクラス `StorageManager` を持ちます。

### 1.1 切り替え基準
1.  `window.electronAPI` が定義されている場合:
    *   **モード**: `local` (ElectronStorageBackend)
    *   **通信先**: メインプロセス（Electron IPC 通信）を介したローカルファイルシステム。
2.  `window.__THINKTANK_MODE__ === 'local'` である場合:
    *   **モード**: `local` (LocalStorageBackend)
    *   **通信先**: 指定されたローカルAPIサーバー（デフォルト `http://localhost:8081`）。
3.  上記以外（ブラウザ直接起動またはOnline環境）:
    *   **モード**: `online` (BigQueryStorageBackend)
    *   **通信先**: 本体のAPIプロキシ経由で Express バックエンド（`/api/bq/*`）。

### 1.2 共通インターフェース（`IStorageBackend`）
すべてのストレージバックエンドは、以下のインターフェースを実装します。

```typescript
export interface ThinkMeta {
  id:          string;
  contentType: string;
  title:       string;
  keywords:    string;
  relatedIds:  string;
  sizeBytes:   number;
  isDeleted:   boolean;
  createdAt:   string;
  updatedAt:   string;
}

export interface SavePayload {
  id:          string;
  contentType: string;
  fullContent: string; // タイトル行 + 本文（TTThink.Content）
  keywords:    string;
  relatedIds:  string;
}

export interface IStorageBackend {
  listMeta(): Promise<ThinkMeta[]>;
  getContent(id: string): Promise<string | null>;
  save(payload: SavePayload): Promise<ThinkMeta>;
  delete(id: string): Promise<void>;
  search(query: string): Promise<ThinkMeta[]>;
}
```

## 2. Electron ローカル保存仕様

デスクトップ版（Electron）では、ユーザーのデータ領域にJSONファイルとして個別データを保存します。

*   **保存ディレクトリ**: `app.getPath('userData')/thinktank/vault/`
*   **ファイル名**: `{id}.json` (IDは `yyyy-MM-dd-HHmmss` 形式)
*   **保存形式**: JSONテキストファイル。構造は `ThinkMeta` に `content`（タイトル行を除いた本文）を加えたもの。
*   **CRUD ロジック**:
    *   `save`: 引数として受け取る `fullContent` から、最初の改行文字 `\n` を探索してタイトル（1行目）と本文（2行目以降）に分割（`splitContent`）します。ローカルに既存のJSONがあれば `createdAt` を維持し、更新日時 `updatedAt` をその時点の ISO 8601 文字列（UTC）に更新して上書き保存します。
    *   `listMeta`: ディレクトリ内のすべての `.json` ファイルを走査し、JSONパースした後に `content` フィールドを取り除いたメタ情報（`ThinkMeta` 互換）の配列を返します。
    *   `delete`: ファイルを直接物理削除するのではなく、JSON内の `isDeleted` フラグを `true` に更新し、`updatedAt` を書き換えて保存（論理削除）します。
    *   `search`: ディレクトリ内のJSONを走査し、`isDeleted === false` のレコードを対象に、検索文字列が `title`、`content`、`keywords` のいずれかに部分一致（大文字小文字無視）するメタデータを抽出します。

## 3. BigQuery クラウド保存仕様

Online（Web）版では、Express バックエンドを経由して Google BigQuery の `thinktank.vault` テーブルにデータを永続化します。

### 3.1 テーブル定義（スキーマ）
*   `file_id` (STRING, REQUIRED): 識別ID
*   `file_type` (STRING, REQUIRED): 固定値 `"md"`
*   `category` (STRING, NULLABLE): コンテンツ種別 (`ContentType`)
*   `title` (STRING, NULLABLE): タイトル行
*   `content` (STRING, NULLABLE): 本文
*   `keywords` (STRING, NULLABLE): キーワード（カンマ区切り）
*   `related_ids` (STRING, NULLABLE): 関連ID（カンマ区切り）
*   `size_bytes` (INT64, NULLABLE): データサイズ
*   `is_deleted` (BOOL, NULLABLE): 論理削除フラグ
*   `created_at` (TIMESTAMP, REQUIRED): 作成日時
*   `updated_at` (TIMESTAMP, REQUIRED): 更新日時
*   **クラスタリング設定**: `category`（ContentTypeごとの検索性能最適化）

### 3.2 SQL制御ロジック
#### 最新メタデータ一覧取得（`listMeta`）
BigQuery は追記型（挿入のみ）で運用されることがあるため、最新の更新データを正しく抽出するクエリを使用します。
```sql
SELECT t.file_id, t.file_type, t.category, t.title,
       t.keywords, t.related_ids, t.size_bytes,
       COALESCE(t.is_deleted, FALSE) AS is_deleted,
       t.created_at, t.updated_at
FROM `[PROJECT].[DATASET].vault` t
INNER JOIN (
  SELECT file_id, MAX(updated_at) AS max_upd
  FROM `[PROJECT].[DATASET].vault`
  WHERE COALESCE(is_deleted, FALSE) = FALSE
  GROUP BY file_id
) latest ON t.file_id = latest.file_id AND t.updated_at = latest.max_upd
WHERE COALESCE(t.is_deleted, FALSE) = FALSE
ORDER BY t.updated_at DESC
```

#### 保存 (Upsert) ロジック (`save`)
同一IDを持つレコードの登録・更新を1つのトランザクションで行うため、`MERGE` 文によるクエリを実行します。
```sql
MERGE `[PROJECT].[DATASET].vault` AS target
USING (
  SELECT @file_id AS file_id, @file_type AS file_type, ...
) AS source ON target.file_id = source.file_id
WHEN MATCHED THEN UPDATE SET
  target.category = source.category,
  target.title = source.title,
  target.content = source.content,
  target.keywords = source.keywords,
  target.related_ids = source.related_ids,
  target.size_bytes = source.size_bytes,
  target.is_deleted = source.is_deleted,
  target.updated_at = source.updated_at
WHEN NOT MATCHED THEN INSERT
  (file_id, file_type, category, title, content, keywords, related_ids, size_bytes, is_deleted, created_at, updated_at)
VALUES
  (...)
```

#### 並列更新競合エラー（Concurrent Update）自動リトライ
BigQuery 上で複数のペインや自動保存が同時に `MERGE` クエリを発行した場合、BigQueryの仕様により `concurrent update` エラー（invalidQuery）が発生することがあります。
これを回避するため、エラーを検知した場合は以下のようにリトライを行います。
*   エラーメッセージに `concurrent update` が含まれる場合、自動で待機時間を設けて再帰的に再試行します。
*   待機時間: `(4 - 残りリトライ回数) * 2000 ms`（指数バックオフ的待機。1回目: 2秒、2回目: 4秒、3回目: 6秒）。
*   最大リトライ回数: `3` 回。

#### 全文検索 (`search`)
最新かつ削除されていないレコードに対し、SQL関数 `CONTAINS_SUBSTR` を利用してメタデータと本文をマージした文字列から部分一致検索を行います。
```sql
WHERE COALESCE(t.is_deleted, FALSE) = FALSE
  AND CONTAINS_SUBSTR(CONCAT(COALESCE(t.title,''), ' ', COALESCE(t.content,'')), @q)
```

## 4. ローカル・サーバー間の同期制御および差分同期アルゴリズム

Local モードでは、クラウドデータベース（BigQuery）との自動・手動同期の有効/無効（on/off）を設定できます。

### 4.1 クラウド同期のon/off設定
*   **設定プロパティ名**: `cloudSyncEnabled` (boolean)
*   **初期値**: `true` (デフォルトで同期有効)
*   **保存先**: UI状態管理（`__tt_ui_state__`）または `localStorage`
*   **挙動制御**:
    *   `cloudSyncEnabled === true` (オン):
        *   手動同期トリガー（`syncFromServer`）を実行可能。
        *   起動時の自動メタデータ確認・差分インポートや、保存時の非同期アップロードキュー（SyncQueue）の処理を実行する。
    *   `cloudSyncEnabled === false` (オフ):
        *   手動同期トリガー（`syncFromServer`）の実行要求があった場合、同期処理を行わず即座に処理をスキップ（またはエラー警告を表示）する。
        *   起動時の自動同期処理や非同期のバックグラウンド更新処理を完全に抑止する。
        *   外部ネットワーク（Express / BigQuery サーバー）へのデータ同期リクエストを行わず、純粋なスタンドアロンのローカルストレージとして動作する。

### 4.2 差分同期アルゴリズム（`syncFromServer`）

クラウド同期が有効（`cloudSyncEnabled === true`）かつデスクトップ版（Electron / Localモード）を起動した状態で同期を実行すると、ローカル環境にクラウドサーバー（BigQuery）の最新データをインポートします。

1.  **同期有効判定**: `cloudSyncEnabled` が `false` の場合は同期をスキップし、空の結果オブジェクトを返却します。
2.  **サーバーメタの取得**: サーバーのAPIエンドポイント `/api/bq/files/meta` から、最新のメタデータ一覧（`serverMetas`）を一括取得します。
3.  **差分の走査**: `serverMetas` の各エントリについて、ローカルの対応するファイルパス（`{id}.json`）を確認します。
4.  **比較とスキップ判定**:
    *   ローカルに `{id}.json` が存在し、ローカルデータの `updatedAt` がサーバー側の `updatedAt` と同等か、より新しい（`local.updatedAt >= server.updatedAt`）場合は、更新不要と判定し処理をスキップ（`skipped++`）します。
5.  **コンテンツのダウンロードと保存**:
    *   スキップ判定から外れた（ローカルに存在しない、またはサーバー側が新しい）場合、サーバーの `/api/bq/files/{id}/content` から本文データを個別取得します。
    *   取得したメタデータと本文データをマージして `{id}.json` を構築し、ローカルファイルシステムに上書き保存します。
    *   ローカル新規作成なら `added++`、上書き更新なら `updated++` としてカウントします。
6.  **結果の返却**: 同期終了後、`{ added, updated, skipped, total }` の結果オブジェクトを返却します。
