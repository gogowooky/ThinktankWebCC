- 文書状態：構想案 v0.1（要レビュー）
- 作成日：2026-10-16
- 対象リポジトリ：ThinktankWebCC
- 確認ブランチ：`TTWebCC260926BigChange`
- 想定利用者：開発責任者、薬事、臨床、非臨床、CMC／製造、品質保証、プロジェクト管理、経営判断者

## 1. 構想の要約

本アプリの目的は、再生医療等製品の「治験入り」を一つの巨大なタスクリストとして管理することではない。Portfolio、Program、Task、Strategyの4視点を行き来しながら、科学的・薬事的な論点、根拠資料、意思決定、実行、承認、残余リスクを一貫して追跡できる業務基盤を作ることである。

中核方針は次のとおりとする。

1. **4視点を同一データの異なる投影として扱う。** 4パネルごとに情報を複製せず、同じ業務オブジェクトをPortfolio、Program、Task、Strategyの観点から表示する。
2. **チャットは原則として独立させる。** ある会話の全文や暫定推論を他の会話・上位階層へ自動流入させない。
3. **上位共有は「情報の昇格」に限定する。** 会話から抽出した決定候補、リスク、根拠、アクション等を人が確認し、必要なものだけをTask、Program、Portfolioへ昇格する。
4. **管理はイベント駆動とする。** 保存済みの事実をイベントとして記録し、そのイベントから進捗、通知、ゲート状態、AI処理を更新する。
5. **AIはProvider共通契約の背後に置く。** OpenAI、Claude（Anthropic）、Geminiを交換可能にし、モデル固有仕様を業務ロジックへ漏らさない。
6. **Orchestratorが複数AIを協働させる。** AIごとに役割を持たせても、参照範囲、実行権限、承認境界、結果の統合はアプリ側が制御する。
7. **人の承認を最終境界にする。** AIは整理・抽出・比較・提案を行うが、薬事方針、臨床判断、正式承認、規制提出、外部送信、完了確定を単独で実行しない。

この構想はThinktankWebCCの既存資産を捨てて作り直す案ではない。既存4パネル、`ContextService`、`AgentService`、`AIProvider`、Bundle／Think、本人確認済みの進捗記録を基礎に、共有境界、イベント、昇格、統括実行、監査性を段階的に追加する。

## 2. 「治験入り」の定義と管理対象

「治験入り」は組織や品目によって意味が異なるため、システム上は単一の固定状態にしない。少なくとも次のマイルストーンを区別し、対象品目ごとに正式な完了条件を定義する。

- 開発方針と規制経路の合意
- PMDA相談方針、相談資料、照会・回答の管理
- 品質／CMC、GCTP、非臨床、安全性の必要資料の充足
- 治験実施計画書、治験薬概要書、説明・同意文書等の準備
- 治験届、IRB／治験審査委員会、医療機関契約、治験製品供給、教育等の準備
- Site activation、被験者登録開始、First Patient Inなど、組織が採用する開始判定

したがって、上位の「治験入り準備完了」は、下位Taskの件数やAIの要約だけから自動判定しない。あらかじめ定義したGateと必須Evidenceがそろい、権限を持つ人が承認した時だけ成立する。

### 2.1 管理対象の基本単位

| オブジェクト | 意味 | 例 |
|---|---|---|
| Portfolio Item | 投資・優先順位を比較する開発候補 | 細胞製品A、適応症B |
| Program | 治験入りまでの統合計画 | 品質、非臨床、薬事、臨床、製造、施設立上げを束ねる計画 |
| Workstream | 専門領域別のまとまり | CMC、非臨床、安全性、臨床、薬事、QA |
| Task | 担当者が完了条件を持って進める作業 | プロトコル案の選択基準を確定する |
| Decision | 採用された判断と理由 | 用量漸増設計を採用する |
| Evidence | 判断・提出・検証を支える根拠 | 試験報告書、相談記録、規格根拠、文献 |
| Risk／Issue | 不確実性または顕在化した問題 | 原材料変更の同等性説明が不足 |
| Gate | 上位マイルストーンの承認点 | PMDA相談実施可、治験届提出可 |
| Chat | 特定目的の独立した検討空間 | 非臨床ギャップ分析、相談資料レビュー |

## 3. 4視点とThinktankWebCCの4パネル

4パネルは4種類のデータベースではなく、同じ正本を異なる判断粒度で見るUIとする。パネル名の即時変更は必要なく、まず役割を対応付ける。

| 視点 | 中心となる問い | 主な表示・操作 | 既存パネルとの対応 |
|---|---|---|---|
| **Portfolio** | どの開発候補へ、なぜ資源を配分するか | 候補比較、優先順位、投資継続／停止、全体リスク、横断依存 | **Thinktank**。現行のVault横断検索、相談開始、課題化を入口として拡張 |
| **Program** | 一つの治験入り目標をどう統合管理するか | Workstream、マイルストーン、依存関係、Gate、主要Decision／Risk、クリティカルパス | **Seeds**。現行のBundle俯瞰、目的・論点・資料・サブ課題・進捗表示をProgram Masterへ拡張 |
| **Task** | 次に誰が何を行い、何をもって完了とするか | 個別検討、資料編集、成果物、担当、期限、ブロッカー、レビュー | **Discuss**。現行の複数Pane、編集、比較、Chat、サブ課題を実行ワークスペースとして活用 |
| **Strategy** | 結果を踏まえて方針をどう見直すか | 前提検証、シナリオ、継続／再検討／停止、学習、次のProgram方針 | **Harvest**。現行の振り返り用Chatを、結果照合と戦略更新へ拡張 |

### 3.1 視点間の原則

- Taskの完了が即座にProgramの完了を意味するわけではない。
- Programの遅延がPortfolioの中止を自動決定するわけではない。
- Strategyは単なる事後メモではなく、前提・結果・学習を比較して次の意思決定を作る。
- Portfolioには全チャットを表示せず、昇格済みのDecision、Risk、Gate、主要Evidence、KPIだけを既定表示する。
- 各パネルの情報には必ず元データへのリンクを持たせ、集計値からTask、Evidence、承認履歴へ遡れるようにする。

## 4. チャット独立と選択的な上位共有

### 4.1 チャットを独立させる理由

再生医療開発では、専門領域ごとに未確定仮説、反証、機密度、責任者が異なる。すべての会話を一つの長大な履歴へ統合すると、古い仮説が最新決定に混入し、アクセス権を越えて情報が拡散し、どの根拠を使った判断か追えなくなる。

各Chatは次を固定して開始する。

- `chatId`、目的、対象Task／Program
- 参照可能なEvidenceと`contextSnapshotId`
- 利用者・役割・アクセス範囲
- 許可されたAI Provider／モデル／ツール
- 外部検索、ファイル生成、外部送信の可否
- 保存期間、機密区分、個人情報・患者情報の取扱区分

他のChatの本文は既定で参照しない。必要な場合も「別Chatの全文を共有」ではなく、そのChatから承認済み情報を昇格させる。

### 4.2 情報の昇格

会話中の発言やAI回答は、そのまま正本ではない。次の状態遷移を経て業務情報へ昇格する。

`Chat Local Draft → Promotion Candidate → Human Review → Approved Record → Upper-level Projection`

昇格対象は、自由文のコピーではなく型を持つ。

- Decision：何を決めたか、選択肢、理由、決定者、発効日
- Evidence：根拠、版、出典、適用範囲、限界
- Risk／Issue：事象、影響、確率、検知条件、対応、Owner
- Assumption：前提、検証方法、期限、反証条件
- Action：担当、期限、完了条件、依存関係
- Gate Result：評価基準、充足Evidence、逸脱、承認者
- Learning：期待と結果の差、再利用条件、次回への提言

### 4.3 共有レベル

| レベル | 見える範囲 | 既定の内容 |
|---|---|---|
| Chat Local | 当該Chat参加者 | 全会話、下書き、AI推論候補 |
| Task Shared | Task関係者 | 承認済みAction、Decision、Evidence、Risk |
| Program Shared | Program関係者 | 上位影響がある項目、Gate、依存関係、主要リスク |
| Portfolio Shared | 経営・Portfolio権限者 | 投資判断に必要な集約情報、重大リスク、主要Gate |

昇格時には、`sourceChatId`、`sourceTurnId`、`sourceSnapshotId`、元資料ID・ハッシュ、抽出したAIとモデル、提案者、レビュー者、承認時刻、変更理由、直前版を保存する。上位レコードを更新する時も過去版を消さず、新版による置換または廃止として記録する。

### 4.4 上位共有のガードレール

- AIによる自動抽出はCandidate作成までとする。
- 決定者が明確でない発言はDecisionへ昇格できない。
- 引用元の版が変わった場合は「根拠再確認待ち」にする。
- 患者識別情報、施設機密、契約情報は、上位集約前にマスキングまたは共有可否確認を必須とする。
- 上位サマリーから元Chatへ戻る権限がない利用者には、許可されたEvidenceだけを表示する。

## 5. イベント駆動型の業務管理

### 5.1 基本形

画面操作やAI提案を直接「現在状態」へ上書きするのではなく、まずCommandとして受け付け、検証後にDomain Eventを確定する。各パネルの状態、通知、ダッシュボードはイベントから更新する。

例：

1. 利用者がAI提案を確認し「RiskとしてProgramへ昇格」を実行する。
2. `PromoteRisk` Commandが権限、元資料、必須項目、版競合を検証する。
3. `RiskPromoted` Eventを一度だけ記録する。
4. Programのリスク一覧、Portfolioの重大リスク集計、担当者通知が更新される。
5. AI Orchestratorは必要なら対応Task案を作るが、自動承認はしない。

### 5.2 主要イベント例

- `ProgramCreated`
- `TaskCreated` / `TaskBlocked` / `TaskCompletionProposed` / `TaskCompletionApproved`
- `EvidenceRegistered` / `EvidenceVersionChanged` / `EvidenceInvalidated`
- `DecisionProposed` / `DecisionApproved` / `DecisionSuperseded`
- `RiskRaised` / `RiskEscalated` / `RiskMitigated`
- `PromotionRequested` / `PromotionApproved` / `PromotionRejected`
- `GateReviewRequested` / `GateApproved` / `GateRejected`
- `AgentRunRequested` / `AgentRunStarted` / `AgentRunFailed` / `AgentOutputAccepted`
- `RegulatoryConsultationScheduled` / `RegulatoryQuestionReceived` / `RegulatoryResponseApproved`
- `ProviderPolicyChanged` / `ModelVersionChanged`

### 5.3 実装上の要件

- Eventには一意ID、発生時刻、記録時刻、Actor、対象、`correlationId`、`causationId`、スキーマ版を持たせる。
- 同じCommandの再送で二重実行しないようIdempotency Keyを使う。
- 正本更新とEvent発行の不整合を避けるため、同一トランザクションまたはTransactional Outboxを使う。
- Event consumerは再実行可能にし、失敗を隠さず再試行回数とDead-letter状態を記録する。
- 日付待ち、外部回答待ち、定例レビューもTimer Eventとして扱い、単なる画面ポーリングに依存しない。
- イベントソーシング全面採用を初期条件にしない。まず既存正本＋追記型監査イベント＋Projectionの構成から始める。

## 6. 共通AI Providerと複数AI協働

### 6.1 Provider共通契約

OpenAI、Claude（Anthropic）、Geminiは、共通の業務契約を実装するAdapterとして扱う。画面や業務サービスが各社API形式を直接扱わない。

共通契約に必要な要素は次のとおりである。

- Provider名、モデルID、モデル版または利用時点
- 能力宣言：テキスト、構造化出力、画像、ファイル、ツール、長文、ストリーミング等
- データ取扱属性：保存、学習利用、保持期間、処理地域、契約上の制約
- `generateStructured`、`generateText`、`stream`、`cancel`
- 標準化した使用量、遅延、終了理由、拒否、再試行可否、Provider request ID
- 共通エラー分類：認証、制限、入力超過、タイムアウト、安全拒否、形式不正、Provider障害
- 構造化出力のアプリ側再検証

OpenAIについては、公式ドキュメントがResponses API上の組込みツール、関数呼出し、remote MCP等を案内している。ただし、本構想ではProviderの機能を直接信頼せず、利用可能ツールと承認境界をアプリ側で制御する。参考：[OpenAI API - Using tools](https://developers.openai.com/api/docs/guides/tools)

### 6.2 Provider選択

Provider／モデル選択は、好みだけでなく次のPolicyで決める。

- データ機密区分と契約条件を満たすか
- 必要能力を備えるか
- 構造化出力の品質評価を通過しているか
- 対象業務に対する社内評価結果
- コスト、応答時間、可用性
- 障害時の代替可否
- 規制対象記録を扱う場合の変更管理、再現性、監査可能性

モデル名の自動置換は行わない。変更時は評価セット、期待出力、既知の失敗、承認者を記録し、影響を受けるAgentだけを段階的に切り替える。

### 6.3 Orchestratorの責務

Orchestratorは「一番賢いAI」ではなく、権限を持つ制御サービスである。

- 目的をWork Itemへ分解する
- 必要な専門AgentとProviderを選ぶ
- 各Agentへ最小限のContextSnapshotと許可ツールを渡す
- 並列実行、依存順実行、タイムアウト、中断、再試行を管理する
- 出力スキーマ、引用、根拠範囲、相互矛盾を検証する
- 複数案を統合してPromotion Candidateまたは成果物候補を作る
- 人の承認が必要な箇所で停止する
- 実行記録を`AgentRun`と監査イベントへ残す

### 6.4 想定する専門Agent

| Agent | 主な役割 | 自動化の上限 |
|---|---|---|
| Program Manager Agent | 依存関係、期限、Gate、クリティカルパスの整理 | 計画変更案まで |
| Regulatory Agent | 規制経路、相談論点、提出資料ギャップの整理 | 薬事判断・提出は不可 |
| CMC／GCTP Agent | 製造、規格、安定性、原材料、変更影響の整理 | 品質承認は不可 |
| Nonclinical Agent | 非臨床パッケージと臨床開始条件のギャップ整理 | 安全性の最終判断は不可 |
| Clinical Agent | プロトコル要素、運用準備、施設課題の整理 | 医学的判断・被験者適格性確定は不可 |
| Evidence Agent | 引用、版、出典、矛盾、欠落の検証 | 証拠の採否決定は不可 |
| QA／Audit Agent | 必須記録、監査証跡、逸脱候補の確認 | CAPA承認・監査結論確定は不可 |
| Strategy Agent | 前提、シナリオ、結果差分、継続条件の比較 | 投資・中止決定は不可 |

複数AIの一致は正しさの証明ではない。同じ誤った根拠に依存する可能性があるため、Evidence Agentによる出典確認と人の専門レビューを別に置く。

## 7. ThinktankWebCCの現行資産との対応

### 7.1 既存4パネル

現行実装はすでに次の基礎を持つ。

- Thinktank：Vault全体の検索・絞り込み、相談開始、Bundle作成、相談の課題化
- Seeds：Bundle内資料、課題概要、親子課題、到達状態、Agentジョブ、外部連携の俯瞰
- Discuss：複数Paneでの閲覧・編集・比較、Chat、成果物作成
- Harvest：担当Chatの表示。戦略見直しや学習抽出は未完成

このため、4視点は新しい画面を一度に追加するより、既存パネルの役割を明示し、同一データへのProjectionを順番に増やす方が安全である。

### 7.2 ContextService

現行`ContextService`は、Bundleに列挙されたIDを起点に資料を解決し、本文ハッシュ、欠落、読込失敗、版未検証等を`ContextSnapshot`へ明示する読み取り専用境界である。子課題と到達状態も要求時に採取でき、Bundle外へ範囲を広げない。

構想ではこれを次のように拡張する。

- `scope`をBundleだけでなくTask、Program、昇格済みPortfolio情報へ一般化する
- Chatごとに固定した`ContextSnapshot`を保存し、後から参照根拠を再構成する
- 機密区分、用途、利用者権限、Provider送信可否をSnapshot作成時に評価する
- Evidenceの版変更を検出し、依存するDecision／Gateへ再確認Eventを出す
- Snapshot本文を全保存するか、ハッシュ＋不変保管先参照にするかを規制・容量要件で決める

### 7.3 AgentService

現行`AgentService`はBundle限定の要約・比較ジョブについて、作成、実行、キャンセル、再試行、Provider／モデル記録、成果物候補、本人確認後の適用、保存競合防止を持つ。これは有用な実行基盤だが、Programを継続管理するOrchestratorではない。

拡張方針は次のとおりとする。

- 現行ジョブを`AgentRun`の最初の実装として保持する
- `job kind`を固定列挙の要約・比較から、登録制のAgent Definitionへ広げる
- 入力Snapshot、使用ツール、出力、検証結果、承認、コストを実行単位で記録する
- OrchestratorはAgentServiceを呼ぶ側とし、AgentService自身に上位判断を持たせない
- 成果物の「生成」と正本への「適用」を引き続き分離する

### 7.4 AIProvider

現行`AIProvider`にはOpenAI、Gemini、AnthropicのAdapterがあり、共通の構造化応答を生成する。APIキーをサーバー側に置き、OpenAIでは`store: false`を指定し、Providerごとの差をAdapter内に閉じ込めている点は継承できる。

一方、現行契約は主に会話生成の`generate`であり、能力交渉、ツール権限、使用量、保持条件、モデル変更管理、複数Agent実行は未整備である。Provider Registry、Capability Policy、標準Telemetryを追加し、会話と業務実行の双方から利用する。

### 7.5 追加するサービス境界

| サービス | 責務 |
|---|---|
| PromotionService | Chatから業務レコードへの昇格候補、レビュー、承認、上位共有 |
| EventService／Outbox | Domain Eventの確実な記録・配信、再試行、監査 |
| OrchestratorService | 複数Agentの計画、実行、統合、承認待ち |
| ProviderRegistry | Provider能力、利用Policy、モデル版、評価状態 |
| ProgramProjectionService | Workstream、Gate、依存関係、主要Riskの投影 |
| PortfolioProjectionService | 複数Programの比較、優先順位、資源・重大リスクの投影 |
| ComplianceLedger | 承認、電子署名、版、変更理由、監査証跡の検索可能な記録 |

## 8. データと監査の設計

### 8.1 正本と派生物

- 正本：承認済みのTask、Decision、Evidence、Risk、Gate、署名・承認記録
- 会話記録：検討過程。正本とは分離する
- AI出力：提案または成果物候補。承認前は正本ではない
- Projection：イベントと正本から再生成できる一覧・ダッシュボード
- Cache／Embedding：検索補助。元資料の代替ではなく、削除・再生成可能にする

### 8.2 必須メタデータ

すべての重要レコードに、少なくとも次を持たせる。

- 永続ID、スキーマ版、作成者、作成時刻、更新者、更新時刻
- 変更前後、変更理由、承認者、承認時刻
- 元資料ID、版、ハッシュ、引用位置、Snapshot ID
- AI関与の有無、Provider、モデル、指示の版、実行ID
- 機密区分、アクセスPolicy、保持期限
- `status`と、その状態を確定したEvent ID

### 8.3 変更ルール

- 承認済みDecision、Gate、Evidenceを物理上書きしない。
- 訂正は新版を作り、旧版との関係と理由を残す。
- 削除は原則として論理削除とし、規程に基づく保持・廃棄を別管理する。
- 一覧上の「最新」は自動的な「正しい」を意味しない。承認状態と発効期間を使う。
- システム時刻、利用者識別、権限変更、失敗した操作も監査対象にする。

## 9. 代表的な利用フロー

### 9.1 非臨床ギャップがProgramへ昇格する例

1. Discussで「非臨床安全性ギャップ」Chatを開始し、対象Evidenceを固定する。
2. Nonclinical Agentが不足項目を候補として抽出し、Evidence Agentが引用と版を検証する。
3. 担当者が内容を確認し、`Risk`と`Action`の昇格を申請する。
4. 責任者の承認で`RiskPromoted`と`TaskCreated`が確定する。
5. SeedsのProgram Masterへ依存関係とGate影響が表示される。
6. 重大度が基準を超える場合だけThinktankのPortfolioへ集約表示される。
7. 対応完了後、Riskを単純削除せず、対策Evidenceと承認を付けて`RiskMitigated`にする。

### 9.2 戦略見直しの例

1. マイルストーン結果またはPMDA相談結果をEvidenceとして登録する。
2. Harvestで当初Assumption、期待結果、実結果、未解決事項を比較する。
3. Strategy Agentが継続、変更、保留、中止の選択肢と根拠を提示する。
4. 人がDecision候補をレビューし、必要に応じてPortfolio承認へ昇格する。
5. 承認されたDecisionからProgram再計画Eventを発行する。

**完了条件**：一つの治験入りProgramについて、主要Gateから根拠Task・Evidence・承認まで往復できる。

- Thinktankに複数Program比較、主要Gate、重大Risk、資源見通しを追加

**完了条件**：上位判断者が要約から根拠へ遡れ、下位Chatの不要な情報を閲覧せずに判断できる。

**完了条件**：承認された用途について、意図した機能、データ完全性、復旧、監査、教育が確認されている。

## 11. 規制・承認・監査上の注意点

### 11.1 規制経路を混同しない

薬機法に基づく承認申請のための治験と、再生医療等安全性確保法等に基づく臨床研究・提供は、手続、責任、審査、記録が同一ではない。Program開始時に対象経路を明示し、テンプレート、必須Gate、承認者を切り替える。PMDAは再生医療等製品の開発前、非臨床、品質、治験手続等について相談区分を設けているため、個別品目の計画は早期に相談戦略へ落とす。参考：[PMDA 再生医療等製品の治験相談等](https://www.pmda.go.jp/review-services/f2f-pre/consultations/0035.html)

### 11.2 GCP、GCTP、信頼性基準への接続

再生医療等製品には専用のGCP省令・関連通知があり、品質・製造ではGCTP、申請資料では信頼性確保が問題となる。アプリの「完了」は、単なるタスク完了ではなく、該当する必須文書、レビュー、承認、逸脱、変更影響がそろっているかをGateで確認する。規制要件は固定文言をコードへ埋め込まず、版管理されたRequirement Setとして管理する。参考：[PMDA 再生医療等製品GCP関連通知](https://www.pmda.go.jp/review-services/inspections/drugs/0005.html)

### 11.3 電磁的記録と電子署名

規制提出資料や原資料、法令上保存すべき記録として本アプリのデータを使う場合、単なる操作ログでは足りない。利用目的に応じたコンピュータ・システム・バリデーション、アクセス管理、作成・変更・削除の責任所在、変更前情報、監査証跡、バックアップ、見読性、保存性、電子署名と記録の結び付きを設計する。参考：[厚生労働省 ER/ES指針](https://www.mhlw.go.jp/web/t_doc?dataId=00ta8216&dataType=1&pageNo=1)

### 11.4 AI固有の統制

- AI出力を原資料、本人の決定、承認済み記録として自動登録しない。
- Provider、モデル、指示、入力Snapshot、ツール、出力、後処理、検証結果を記録する。
- モデル更新時は、承認済み用途ごとに回帰評価と変更承認を行う。
- 重要な数値、適格性、安全性シグナル、規制解釈、引用は人が原資料で確認する。
- AIが生成した要約だけをGateの根拠にせず、元Evidenceを必須にする。
- Prompt Injectionを含む資料を命令として実行しない。資料は常に参照データとして扱う。
- 複数AIの多数決を承認の代用にしない。

### 11.5 個人情報・医療情報・機密情報

- 初期版では患者識別情報、原データ、未マスキング症例情報を外部AIへ送らない。
- データ最小化、仮名化、最小権限、暗号化、持出し制御、保持・削除、インシデント対応を定める。
- 外部Providerについて、委託先評価、契約、再委託、保存・学習利用、処理地域、越境移転、削除、事故通知を確認する。
- 医療機関の医療情報システムと接続する場合は、責任分界、認証・認可、ログ、バックアップ、BCP、サイバーセキュリティを追加評価する。参考：[厚生労働省 医療情報システムの安全管理に関するガイドライン第7.0版](https://www.mhlw.go.jp/stf/shingi/0000516275_00006.html)
- 個人情報の取扱いは対象組織・データに応じて最新のガイダンスを確認する。参考：[個人情報保護委員会 医療関連分野ガイダンス](https://www.ppc.go.jp/personalinfo/legal/guidelines/)

### 11.6 承認と責任分界

最低限、次をシステム上で区別する。

- 作成者と承認者
- 業務レビューと品質保証レビュー
- AI提案の採用と正式Decisionの承認
- 文書内容の承認と電子署名
- Task完了とGate承認
- 技術的送信成功と規制上の受理

権限のある人が画面上で承認したこと、何を承認したか、その時点の版、署名の意味を後から説明できなければならない。

## 12. 非機能要件

| 分類 | 要件 |
|---|---|
| 可用性 | AI Provider停止時も正本閲覧・編集・承認・監査検索が可能 |
| セキュリティ | SSO／MFA、Roleと属性に基づくアクセス、秘密情報のサーバー保管、暗号化 |
| 監査 | 追記型監査証跡、時刻同期、変更前後、失敗操作、定期レビュー |
| データ完全性 | ハッシュ、版競合、参照整合性、バックアップ、復元試験 |
| 性能 | Program画面は集約Projectionを使い、全Chat再読込を要求しない |
| 保守性 | Provider Adapter、Agent Definition、Requirement Setを版管理 |
| 可搬性 | 特定ProviderのConversation IDや独自ツール形式を正本キーにしない |
| 観測性 | AgentRun、Event lag、失敗率、再試行、コスト、承認待ち時間を監視 |

## 13. 初期MVPに含めるもの／含めないもの

### 含める

- 一つの治験入りProgramと3〜5 Workstream

- 医療判断、被験者適格性、投与判断の自動化
- 未マスキング患者情報の外部AI送信
- 全社Portfolioの自動最適化
- AIによるGateの自動承認
- 既存データの一括自動変換
- Provider間の完全な機能同一性の仮定

## 15. 推奨する最初の実装単位

最初は「非臨床またはCMCの一つのギャップを、独立Chatで検討し、RiskとActionへ昇格し、SeedsのProgram Gateへ影響表示し、承認履歴まで残す」という縦切りを実装する。

この一連の流れで、次を同時に検証できる。

- Chat独立
- ContextSnapshot
- 情報の昇格
- Event駆動
- Task／ProgramのProjection
- AI出力と人の承認の分離
- Provider共通化
- 監査証跡

Portfolio最適化や多数の専門Agentを先に作るより、この縦切りで業務境界と証跡を確立した後に広げる方が、既存ThinktankWebCCを活かしながら規制・運用リスクを抑えられる。
