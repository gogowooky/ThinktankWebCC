# AIChat思考支援：実装内容と確認方法

作成日：2026-09-08  
基準：[AIChatによる思考支援とUI運用仕様案](Thinktank_AI_ThoughtSupport_Operation.md)

## 1. 実装した運用

4パネルを必ず通る工程にはせず、相談ごとにAIが必要な視点を選びます。タイトルの種類・担当パネル・状態をAIが判断し、アプリが検証して保存します。

担当変更後も、現在の画面で同じChatを表示し続けます。次の応答には新しい担当の指示と同じ相談の記録が渡ります。「担当をOverviewに引き継ぎました。このまま相談を続けられます」と案内するため、ユーザーはタグ編集やパネル移動を管理する必要がありません。

ユーザー自身が別のパネルで相談を開くこともできます。Bundle分析の「この相談を続ける」からは、担当パネルのAI相談を開けます。

## 2. 思考支援の内容

全領域に、次の共通方針を適用します。

- 本人のペースを尊重し、重要な問いを一つずつ扱う。
- 同じ質問に穏やかに答え、過去と異なる発言を意向変更の可能性も含めて扱う。
- 事実、本人の決定、AIの提案、未確認事項を区別する。
- 再開時に前回・現在・次を示し、中断時に再開メモを残す。
- 未整理の話や将来候補を、勝手に実施義務のあるTODOにしない。
- 分類・担当・記録の整理はAIが担い、本人の意思決定を代行しない。
- 本人確認の日時と、要約を更新した日時を分ける。

説明の長さは「短く、一つずつ」「標準」「詳しく」から選べます。この選択はブラウザ／アプリの設定として保持します。

## 3. 4パネルと個別Pane

| 領域 | 対話の役割と参照範囲 |
|---|---|
| Thinktank | 未整理の相談を受け止め、全Vaultの一覧・検索から対象を探す。全本文を一括でAIに送らない |
| Overview | 対象Chatに固定されたBundleの目的、論点、優先順位、依存、待機を整理する。Bundle未設定で全Vaultへ拡大しない |
| Workout AIChat | 対象課題を具体化し、個別の検討結果を次の行動へつなぐ |
| ReThink | 個別・全体レビューを区別し、記録と現実、完了条件、残課題を確認する |
| Workout Chat Pane | 個別の自由対話。担当・状態の変更を拒否し、説明・比較・成果物作成に使う |

AI相談一覧はTODO、PROJ、ASK、EVNT、LOOPに対応しました。完了・中止は初期表示から除外し、「完了・中止も表示」で読み返せます。相談中のChatは、担当変更や完了によって一覧から突然消えないよう保持します。

OverviewとWorkoutは設定Bundleを基本範囲とし、ReThinkはBundle未設定時には全体から担当相談を選べます。WorkoutではBundleのない単独相談も扱えます。Thinktankには、そこで保存した未整理Chatも残ります。

Chatの対象Bundleは管理情報へ固定します。画面で別Bundleを選んでも、進行中の相談の所属や参照範囲は変更しません。明示した `[chat:ID]` は追加参照として扱います。

## 4. タイトルと保存

```text
{種類}:{担当パネル}｜[{状態}]{相談名}
PROJ:Overview｜[進行中]交流会の準備
```

対応状態は、未着手・進行中・待機・保留・完了・中止です。状態のない既存タイトルに状態を推測して補うことはしません。従来の小文字を含む管理タイトルも読み取ります。

管理情報の正本は、Chatの `Metadata.thoughtSupport` です。小さな相談でも別の回覧板Memoを必須にはしません。

保存する主な情報：目的、完了条件、現在の状況、次の一手、再開メモ、決定・未決定・AI提案、待機理由、残課題の扱い、対象Bundle、親子・依存・繰り返し元、参照資料、日時、本人確認、引き継ぎ理由、変更履歴。

会話は従来の読めるChat本文に保存し、複数行の発言や見出し・時刻を正確に復元するため、メタデータにもメッセージ配列を保持します。TextEditorで本文を編集した場合は、古いメッセージ配列で編集を消さず、本文を優先して読み直します。

ユーザーの入力はAIへ問い合わせる前に保存し、応答と管理変更は応答完了後に保存します。AIとの通信が途中で終わった場合やJSONの形式が不正な場合は、管理変更を適用しません。

## 5. AIの判断とアプリの操作

既存のモデル選択を利用します。Anthropic、OpenAI、Geminiに同じ応答契約を渡し、応答本文と操作内容をJSONで受け取ります。思考支援の要求では、旧Gemini専用のBigQuery直接保存ツールと旧固定プロンプトを使用しません。

アプリ側の共通操作が、次の処理を担当します。

1. 許可された範囲での検索と本文取得。
2. 種類・担当・状態・管理情報の検証と保存。
3. 必要なBundle、子課題、Memo・Table・Link・HTML成果物の作成。
4. Bundleへの重複のない登録と、IDによる関連付け。
5. 個別Paneの成果を、管理Chatの参照・確認事項として取り込む。

完了・中止や決定事項の変更では、今回の本人の発言に一致する根拠引用が必要です。終了時は残課題の扱いも必要とします。発言の意味が明確な同意かどうかはAIの対話方針で判断し、引用の存在だけで意味の正しさまで機械的に保証するものではありません。

Paneの「結果を相談につなぐ」では、反映先を選んで参照と確認事項を保存します。本人の決定としては自動登録しません。同じPaneの同じ版を繰り返し反映しても、確認事項を重複追加しません。

## 6. 失敗・競合・取り消し

- 管理変更は内容と版を照合し、別の場所で変更された相談を無断で上書きしない。
- 保存に失敗した場合は、画面に応答とエラーを残し、「保存を再試行」を表示する。
- 複数ファイル操作は、応答と同時に未完了操作の記録を保存する。中断後も未完了操作を再試行できる。
- 子課題・LOOP各回には相談IDと識別キーから決まるIDを用い、再試行時に同じものを重複作成しない。
- 複数ファイル全体を一括のデータベーストランザクションにはしていない。途中で作成できたファイルは残し、残りの登録を完了する方式。
- 「直前の管理変更を戻す」は、タイトルと管理情報を以前の状態に戻す。会話や作成済み資料は削除しない。

## 7. ストレージ別の対応

| 保存先 | 対応 |
|---|---|
| BigQuery | 既存のmetadata保存と更新日時の競合検出を利用 |
| Electron | metadataを保存・同期対象に追加。保存用ロックと更新日時照合を行い、一時ファイルから置き換える |
| 別プロセスのC# Local API | metadata列のない旧APIとの互換のため、本文先頭の予約コメントへ管理情報を格納し、アプリに返すときに分離する |

C# Local APIでは、Chat/HTMLの一覧読み込み時に管理情報も取得します。保存前の更新日時確認は行いますが、別実装のC#サーバー側が原子的な更新条件を提供しないため、複数プロセス間の完全な競合防止までは保証しません。

Electronの保存ロックは通常の終了時に解放されます。保存中にプロセスが強制終了するとロックが残る場合があります。その場合は元データを保護して保存を停止する設計です。

## 8. Bundle分析・HTML・日時

Bundle分析には、目的、現在、次の一手、本人の決定、未決定、AI提案、待機、再確認日、本人確認日を表示します。元の記録を開く操作と、担当AIとの相談を続ける操作を用意しました。

HTMLは既存の独立したThink種別と隔離表示を利用します。AI生成資料には元のChat・資料IDと参照時点を保存し、元の記録が変わった場合は再確認を促します。HTML内から管理状態を変更する機能は追加していません。

開始・終了日時、期限、実施予定、再確認日、再提示日を別々に保持します。不正な日付や開始より前の終了日時は保存を拒否します。再確認・再提示の時期になった相談は、Chatを開いたときとアプリ内の定期的な表示更新で案内します。

LOOPには繰り返しのルールと標準手順を保存でき、対話から各回のTODO・EVNTを作成して関連付けられます。同じ各回を再度作成する要求では既存の記録を利用し、過去の実施内容を上書きしません。

仕様第11節の初期運用に従い、アプリ終了中の通知、無人での定期作成、外部予約・送信は行いません。

## 9. 確認したことと、実利用で確認すること

自動テストでは、共通解析、担当変更後の継続、参照範囲固定、Paneの管理変更拒否、根拠のない完了・決定変更の拒否、保存失敗からの復旧、重複防止、正確な会話復元、ストレージへの永続化を確認します。

実行結果：全15テストファイル・170件が成功。フロントエンドとサーバーの型チェック／ビルドも成功しました。既存の大きな配信チャンクに関するビルド警告は残っています。

UIの送受信テストには模擬AI応答を用いています。実サービスのAIが自然な会話から常に適切に分類・確認・引き継ぎすることまで保証したテストではありません。運用開始時は小さな実例で、説明の長さや確認の頻度を調整してください。

試す例：Thinktankで交流会について相談 → 全体整理へ担当変更 → 会場選びを具体化 → 個別Paneで比較 → 参照を課題へ反映 → 返事待ちを記録 → 再開して現状確認 → 残課題を確認して区切る。パネル移動を手動で判断せず、同じ相談を続けられることを確認できます。

フロントエンドとサーバーの両方を変更しています。反映には再ビルドしたアプリとサーバーの再起動が必要です。Electron版ではメインプロセスの再起動も必要です。
